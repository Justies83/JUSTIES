# 매일 아침 브리핑 — 작업 지침

매일 06:00 (KST) 예약 실행이 이 문서를 읽고 그대로 수행한다.
지침을 고치고 싶으면 이 파일을 고친다. 예약 설정을 건드릴 필요는 없다.

예약 실행이 둘 중 어느 것인지, 어떤 모델로 도는지는 `docs/routines/` 에 있다.
이 문서는 **무엇을 어떻게 쓸지**만 정하고, 실행의 배선은 그쪽이 정한다.

## 목표 — 매일 다섯 편

매일 아침 다음 **다섯 편**을 쓴다. 순서는 재료가 갖춰지는 대로 자유롭게
정하되, 하나씩 끝내고 바로 push한다(아래 "한 편씩 끝내고, 한 편씩
push한다" 참고).

| # | 글 | 무엇을 다루나 | 형식 |
| --- | --- | --- | --- |
| 1 | 미장 요약 | 전날 미국 정규장 마감 정리. 국내 증시 개장일이면 종목·섹터 영향 예측까지 | 단일 기사 |
| 2 | 특별한 뉴스 정리 | 오늘 가장 화제인 소식 한 건을 깊게 | 단일 기사 |
| 3 | 주요 이벤트 정리 | 그 밖에 언급이 많은 소식 여러 건을 묶어서 | 롤업 |
| 4 | 국제 뉴스 정리 | 외교·통상·해외 사건 중 언급이 많은 것을 묶어서 | 롤업 |
| 5 | 어제자 국내 뉴스 정리 | 어제 하루 국내에서 나온 소식 중 언급이 많은 것을 묶어서 | 롤업 |

각 글의 구체적인 지침은 아래 "1번 글 — 미장 요약"부터 "롤업 글 형식"까지에
있다.

선정 기준은 하나뿐이다 — **여러 매체가 같이, 많이 다룬 소식.** "내가
보기에 중요하다"가 아니라 "검색했을 때 같은 소식을 다루는 매체가 여럿
보인다"가 기준이다. 프리프린트나 한 매체만 보도한 단독 기사는 대상이
아니다(과학 섹션의 기존 원칙을 다섯 편 전체로 넓힌 것이다).

편수를 억지로 채우라는 뜻은 아니다. 재료가 부실한 항목은 그날 비워 두고,
왜 못 채웠는지 완료 보고에 적는다. 다만 "하루 최소 한 편"(아래) 원칙은
지킨다 — 다섯 편 모두 재료가 없다고 판단되면 기준을 너무 좁게 잡은 건
아닌지 먼저 의심한다.

### 한 편씩 끝내고, 한 편씩 push한다 — 이것이 가장 중요한 규칙이다

**다섯 편을 다 쓴 뒤에 한꺼번에 커밋하지 않는다.** 한 편을 완성할 때마다 그
자리에서 빌드하고 커밋하고 push한 뒤에 다음 편으로 넘어간다.

이 규칙이 있는 이유는 분명하다. 예약 실행이 다섯 편을 조사하고 쓰는 데는 시간이
오래 걸리고, 마지막에 몰아서 커밋하는 방식에서는 **중간에 실행이 끝나면 그때까지
쓴 글이 전부 사라진다.** 실제로 2026-08-25와 08-26 두 번의 예약 실행이 각각
13분·17분 동안 조사와 작성을 하고도 커밋을 하나도 남기지 못했다. 8월 28일에는
다섯 편 롤업 구조가 갓 도입된 첫 실행에서 21분을 쓰고도 똑같이 커밋이 하나도
없었다 — 롤업 형식이 편당 작업량을 늘린 것이 유력한 원인으로 보여, 롤업 소식
수를 아래처럼 줄였다. 저장소에 있는 글은 전부 대화형 세션에서 쓴 것이다.

따라서 순서는 이렇다.

1. 가장 확실한 재료 한 편을 먼저 고른다 (보통 1번 미장 요약).
2. 그 한 편을 쓴다 → `npm run build` → 통과하면 **즉시 커밋하고 push한다.**
3. 그다음 편으로 넘어가 2를 반복한다.

시간이 부족해 세 편에서 멈추더라도 그 세 편은 이미 사이트에 올라가 있다.
**한 편도 push하지 못한 채 실행이 끝나는 것이 최악의 결과다.**

### 그래도 안 되면 — 다 묶어서라도 한 편은 올린다

다섯 편을 각각 순서대로 시도하다가 **시간이 부족해지는 게 보이면, 다섯 편을
따로따로 완성하려는 시도를 멈추고 그때까지 확인해 둔 소식을 전부 하나의
글로 묶어서 즉시 push한다.** 카테고리 구분 없이, 그날 원문까지 확인된
소식을 모두 모아 "롤업 글 형식"으로 정리한 글 한 편이면 된다(제목 예:
"8월 28일 아침 정리"). **다섯 편을 못 채우는 것보다, 아무것도 못 올리는
것이 훨씬 나쁘다.**

이 판단은 실행이 끝나기 직전이 아니라 **더 일찍** 내린다. 예를 들어 1번
(미장 요약)조차 아직 완성하지 못한 채 주어진 시간의 절반 가까이 썼다면,
그 시점에 바로 지금까지 확인한 사실만으로 짧게라도 정리해 올리는 쪽으로
방향을 바꾼다. "조금만 더 조사하면 제대로 된 다섯 편이 나온다"는 판단을
믿지 않는다 — 지금까지 매번 그 판단이 틀렸다.

### 하루 최소 한 편

다섯 편 모두에서 쓸 만한 것을 찾지 못했다면, 조건을 좁히기 전에 먼저 의심한다 —
정말 그날 확인 가능한 소식이 하나도 없었는가, 아니면 기준을 너무 좁게 잡았는가.

1번(미장 요약)은 사실상 매일 재료가 있다. 국내 증시 마감, 환율, 미국 장 마감은
공개 매체에서 날짜와 수치를 확인할 수 있고, 이 아카이브가 계속 써 온 주제다.
**그날 아무것도 발행하지 못할 상황이라면 최소한 1번은 쓴다.**

한 편도 쓰지 않고 끝내는 것은 사실 확인이 불가능했을 때에 한한다. 그때는 완료
보고에 **어떤 후보를 검토했고 각각 왜 버렸는지** 구체적으로 적는다. "쓸 만한 게
없었다"는 보고로는 다음에 무엇을 고쳐야 할지 알 수 없다.

## 대상 섹션 — 넷뿐이다

다섯 편 각각에 아래 `category` 중 하나를 붙인다. 그날 무엇을 다섯 편으로
쓸지는 위 "목표" 표가 정하고, 아래 표는 그 다섯 편에 붙일 분류 축일 뿐이다.

| 섹션 | `category` | 수집원 |
| --- | --- | --- |
| 경제 · 산업 | `finance` | 국내 증시·환율 개장/마감, 기업 공시 |
| IT · 기술 | `tech` | 반도체·AI 인프라·소프트웨어 발표, 논문 |
| 과학 | `science` | **주요 언론이 크게 다룬 소식만.** 프리프린트 형태(bioRxiv/medRxiv 단신 요약)는 쓰지 않는다 |
| 국제 정세 | `world` | 외교·통상·공급망 |

`research` `review` `parenting` `life` 는 **자동 발행하지 않는다.** 직접 겪고 쓰는
글이며 뉴스로 채울 성격이 아니다.

## 1번 글 — 미장 요약

**매일 쓴다.** 전날 미국 정규장이 정상적으로 열렸다면 그 마감을 정리하는
것이 기본이고, **그날 국내 증시(KRX)가 개장하면** 국내 종목·섹터 영향
예측까지 붙인다. 미국이 휴장이었던 다음 날에는 "미국 휴장으로 특별한
마감 없음"을 짧게 밝히고, 직전 정규장 이후 나온 다른 지표(선물, 국채금리,
환율 등)로 대체할 수 있으면 대체한다. category는 `finance`.

**들어가야 할 것:**

1. **미국 3대 지수 마감** — 다우·나스닥·S&P500의 마감 수치와 등락률, 그리고
   그 마감을 움직인 핵심 요인(실적, 지정학, 금리, 유가 등)을 원문에서 확인해
   적는다.
2. **국내 증시가 그날 개장하면, 국내 관련 종목·섹터에 대한 예측** —
   "미국이 내렸으니 한국도 내린다"처럼 지수 대 지수로 뭉뚱그리지 않는다.
   어떤 소식이 어떤 국내 종목·업종과 구체적으로 연결되는지 짚는다. 같은
   소식이 한쪽엔 악재, 다른 쪽엔 호재로 갈릴 수도 있다 — 예를 들어 미국
   반도체 고객사의 가격 인상 소식은 그 미국 회사에는 비용 부담이지만, 그
   가격을 매기는 국내 메모리 회사에는 오히려 우호적인 신호일 수 있다.
   이런 결을 구분해서 쓴다.
3. **이것은 예측이라는 표시** — 실제 개장 반응과 다를 수 있다는 점을 본문에
   명시한다. 이 글은 개장 **전**에 쓰는 것이 원칙이라, 쓰는 시점에 실제
   결과를 알 수 없는 것이 정상이다.

**출처는 로그인 없이 누구나 열어 확인할 수 있는 공개 매체만 쓴다.** 개인
계정으로 로그인해야 보이는 커뮤니티·플랫폼 데이터는 나중에 누구도 검증할 수
없으므로 쓰지 않는다. CNBC, Motley Fool, 연합인포맥스, 국내 경제지 등 이
아카이브가 지금까지 써 온 것과 같은 기준이다.

## 2번 글 — 특별한 뉴스 정리

오늘 검색했을 때 **가장 많은 매체가 같이 다루고 있는 소식 한 건**을 깊게
쓴다. category는 그 소식의 성격에 맞게 `finance`/`tech`/`science`/`world`
중 하나를 고른다(`science`를 고를 때는 "주요 언론이 크게 다룬 것만" 원칙이
그대로 적용된다). 형식은 기존 단일 기사와 같다 — ## 사실 / ## 해석 /
## 아직 확인되지 않은 것.

## 3번 글 — 주요 이벤트 정리

2번에 넣지 못했지만 여전히 언급이 많은 소식 여러 건을 한 편에 묶는다.
아래 "롤업 글 형식"을 따른다. category는 묶은 소식 중 비중이 가장 큰
것으로 하나 고르고, 나머지 주제는 `tags`로 남긴다.

## 4번 글 — 국제 뉴스 정리

외교·통상·전쟁·해외 정치 등 국외 소식 중 언급이 많은 것을 묶는다. 아래
"롤업 글 형식"을 따른다. category는 `world`.

## 5번 글 — 어제자 국내 뉴스 정리

**어제(발행일 기준 전날) 하루** 국내에서 나온 소식 중 언급이 많은 것을
묶는다. 오늘 새벽에 막 나온 속보는 2·3번 글에서 다루고, 이 글은 어제
하루로 범위를 좁힌다. 아래 "롤업 글 형식"을 따른다. category는 묶은
소식 중 비중이 가장 큰 것(대개 `finance`)으로 고른다.

## 롤업 글 형식 (3·4·5번 공통)

한 편에 소식을 **2~3건만** 묶는다(예전엔 3~5건이었는데, 편당 작업량이
늘어 8월 28일 실행이 통째로 실패했다 — 소식 수를 줄인 이유다). 소식마다
`###` 소제목을 달고, 그 아래 사실 2~4줄과(있다면) 해석 1~2문장을 짧게
쓴다. 단일 기사처럼 글 전체를 사실/해석 두 단으로 나누지 않는다.

```markdown
### <소식 1 제목>
- 사실 불릿…
- 사실 불릿…

한두 문장으로 해석.

### <소식 2 제목>
...
```

글 끝의 "아직 확인되지 않은 것"과 출처는 소식별로 나누지 않고 전체를
묶어 한 번에 정리한다. **원문 확인 의무(발행 날짜·수치 확인)는 소식 하나
하나에 똑같이 적용된다** — 롤업이라고 검증을 건너뛰지 않는다. 확인이 안
되는 소식은 그 소식만 빼고 나머지로 채운다.

## 절차 0 — 요청부터 확인한다

뉴스보다 먼저 확인한다. 사용자가 `/admin` 의 **글 요청** 에서 주제를 넣어 둔다.

```bash
node scripts/pending-requests.mjs
```

대기 중인 요청이 있으면 **그것을 먼저 쓴다.** 뉴스 브리핑보다 우선한다.
사용자가 직접 시킨 일이기 때문이다.

요청 처리 규칙:

- `섹션` `형식` 이 비어 있으면 주제에 맞게 고른다. 지정돼 있으면 그대로 따른다.
- `참고링크` 가 있으면 **반드시 그 원문을 열어** 근거로 쓴다.
- `지시사항` 은 이 문서의 일반 규칙보다 우선한다.
- `초안으로만: true` 면 글에 `draft: true` 를 넣는다. 사이트에는 나타나지 않고
  `npm run dev` 에서만 보인다.
- 요청 주제가 자동 발행 대상 섹션(경제·IT·과학·국제) 밖이어도 **쓴다.** 그 제한은
  뉴스 브리핑에만 적용된다. 사용자가 리뷰나 육아 글을 요청하면 쓰는 것이 맞다.
- 사실 확인이 불가능한 주제(개인 경험, 직접 써 봐야 아는 것)라면 억지로 쓰지 말고,
  요청 파일의 `상태` 를 그대로 두고 무엇이 필요한지 보고한다.

처리를 마치면 **같은 요청 파일을 고친다.**

```yaml
상태: 완료
결과: /posts/2026-08-21-my-post
```

이렇게 해야 다음 실행이 같은 요청을 다시 쓰지 않는다. 요청 파일은 사이트에 발행되지
않는다(Astro는 `src/content/posts/` 만 읽는다).

## 절차 1 — 뉴스

### 1. 수집

`과학` 은 **일반 뉴스에서 주요 언론이 크게 다룬 소식**만 찾는다. 신약·임상
결과·대형 발표처럼 여러 매체가 같이 보도한 것이 대상이다.

**bioRxiv/medRxiv 프리프린트를 훑어 아무 논문이나 요약하는 방식은 쓰지 않는다.**
그날 대서특필된 과학 뉴스가 없어도 프리프린트로 대체하지 않는다 — 며칠을 그렇게
채웠더니 "과학 = 낯선 프리프린트 목록"이 돼 버렸고, 독자가 알 만한 소식은 하나도
다루지 못했다. 대서특필된 과학 뉴스가 없으면 **그날은 과학 섹션을 발행하지 않는다.**
`scripts/fetch-preprints.mjs` 는 저장소에 남아 있지만 이 절차에서는 쓰지 않는다.

모든 섹션은 웹 검색으로 후보를 찾는다.
**MCP 도구에 의존하지 말 것.** 예약 실행 세션에는 MCP 도구가 없다.

### 2. 원문 확인 — 생략 금지

**검색 결과 요약을 근거로 글을 쓰지 않는다.** 반드시 원문을 받아 다음을 확인한다.

- **발행 날짜.** 검색은 오래된 기사를 최신처럼 보여준다. 실제로 1월 기사를 오늘
  소식으로 착각한 사례가 있었다. 날짜가 확인되지 않으면 버린다.
- 숫자, 고유명사, 인용문의 정확한 표기
- 1차 출처(기업 발표·논문·통계)가 따로 있으면 그것도 확인한다

### 3. 작성

`src/content/posts/YYYY-MM-DD-<영문-슬러그>.md` 로 만든다.
본문은 아래 세 부분을 **분리해서** 쓴다. 이 아카이브의 편집 원칙이다.

1. **사실** — 확인된 것만. 수치는 기준 시점을 함께 적는다
   (장중인지 종가인지, 발표일인지 시행일인지).
2. **해석** — 내 판단. 사실과 같은 단락에 섞지 않는다.
3. **아직 확인되지 않은 것** — 다음에 다시 볼 근거가 된다.

- 글 끝에 **출처** 목록을 링크로 남긴다.
- 시장 관련 글에는 "학습 목적의 개인 메모이며 투자 권유가 아니다"를 남긴다.
- 프리프린트는 **동료심사를 거치지 않았음**을 본문에 밝힌다.
- 이전 글과 이어지면 내부 링크로 연결한다 (`/posts/...`).

**물결표는 escape 한다.** 한 단락(또는 목록 항목) 안에 `~` 가 두 번 나오면
마크다운이 그 사이를 **취소선**으로 만든다. 구간 표기가 많은 이 아카이브에서는
반드시 걸린다 — `6~12억원 ... 2028~2029년` 이 한 줄에 있으면 그 사이 전체에
줄이 그어진다. 실제로 그렇게 발행된 적이 있다.

```markdown
과세표준 6\~12억원 구간 ... 최종 구조는 2028\~2029년에 완성된다
```

한 줄에 하나뿐이면 짝이 없어 안전하지만, 세는 것보다 **항상 escape 하는 것**이
싸다. `-5.80%~+6.19%` 같은 등락 구간, `2027~2028년` 같은 연도 구간이 모두 대상이다.

**볼드가 문장부호로 끝나고 그 뒤에 조사가 공백 없이 붙으면 깨진다.**
`**47.2%**를`, `**"전혀 없다"**고`, `**...달러)**뿐` 같은 형태가 모두 이 문제다.
글자로 끝나는 볼드(`동결**됐고`)는 괜찮다 — 문장부호(`%` `"` `)` 등)로 끝날 때만
걸린다. 한국어는 조사가 항상 앞말에 붙기 때문에, 수치·인용을 볼드로 감쌀 때마다
마주치는 문제다.

```markdown
전체 수출의 **47.2%**를 차지했다     ← 깨짐 (** 앞이 %, 뒤가 한글, 공백 없음)
전체 수출의 **47.2**%를 차지했다     ← 정상 (숫자만 볼드, %는 밖으로)
김 장관은 **"이해가 있었다"**고 밝혔다   ← 깨짐
김 장관은 **"이해가 있었다"고** 밝혔다   ← 정상 (조사까지 볼드에 포함)
```

고치는 방법은 둘 중 하나다 — 문장부호를 볼드 밖으로 빼거나, 뒤에 붙는 조사를
볼드 안으로 끌어들인다. 어느 쪽이든 **볼드가 문장부호로 끝나면서 그 뒤에 공백
없는 한글이 오는 조합만 피하면 된다.** 실제로 이 형태로 발행된 글이 여러 편
있었다.

### 4. 이미지

**표지는 자동으로 생성된다.** `cover` 를 비워 두면 `/covers/<파일명>.svg` 가 만들어져
목록과 글 상세에 쓰인다. 분류로 색이, 파일명 해시로 문양이 결정되므로 글마다 다르고
다시 빌드해도 같다. 그림이 없어서 심심할 일은 없으니, **도표는 수치가 의미를 더할 때만
그린다.**

- **언론사 사진과 기업 배포 자료를 쓰지 않는다.** 저작권 문제다.
- 필요하면 기사에 실린 **수치로 도표를 직접 그린다.**
  `scripts/make-charts.mjs` 가 예시다. SVG로 만든다 — 한글이 브라우저 폰트로
  렌더링되고 다크모드에서도 깨지지 않는다.
- 도표를 쓴 글에는 "도표는 위 기사의 수치로 직접 작성했다"를 남긴다.
- 사진이 여러 장인 글은 `gallery` 항목을 쓴다.

도표의 규격은 기존 것과 맞춘다. `scripts/make-charts.mjs` 를 그대로 참고하면 된다.

| 항목 | 값 |
| --- | --- |
| 캔버스 | `viewBox="0 0 900 520"` — 글 칼럼(704px)에 맞는 비율 |
| 배경 | `#f4f1ea` (종이색). 흰색으로 두면 본문 배경에서 흰 판처럼 튄다 |
| 선 · 강조 | `#16756a` (틸), `#e0795b` (산호) |
| 글자 | 잉크 `#20231f`, 보조 `#62655d` |
| 캡션 | 도표 안 아래쪽에 기준 시점·축 설명을 mono로 남긴다 |

글 상세의 제목·대표 이미지·본문·사진 격자·푸터는 **모두 같은 폭(`--article`)** 으로
정렬된다. 대표 이미지는 잘리지 않고 전체가 보인다(`object-fit: contain`). 도표에 제목이나
축 이름을 넣어도 안전하다.

### 5. 검증 후 커밋 — 한 편 쓸 때마다 바로

한 편을 다 썼으면 **다음 편으로 넘어가기 전에** 여기까지 마친다.

```bash
npm run build      # 프론트매터가 틀리면 여기서 실패한다
npx astro check
git add src/content/posts/<이번-글>.md public/covers 2>/dev/null
git commit -m "<이번 글 제목>"
git push -u origin claude/personal-editable-homepage-31hofg
```

push까지 끝난 것을 확인한 뒤에 다음 글을 시작한다. **배포는 GitHub Actions가
한다.** Cloudflare 토큰이 필요 없다.

빌드가 실패하면 그 글만 고친다. 고쳐지지 않으면 그 글은 버리고 다음 글로
넘어간다 — 한 글 때문에 나머지를 못 올리는 일이 없어야 한다.

push가 거부되면 (다른 실행이 먼저 push한 경우) 다음을 하고 다시 push한다.

```bash
git pull --rebase origin claude/personal-editable-homepage-31hofg
```

## 발행하지 않아야 할 때

다음 중 하나라도 해당하면 그 항목을 버린다. 전부 버려도 된다.

- 원문에서 날짜를 확인할 수 없다
- 수치의 출처가 "업계 추정" 뿐이고 원 통계를 찾을 수 없다
- 같은 내용을 최근 3일 안에 이미 썼다
- 확인에 시간이 더 필요하다 — 이때는 `draft: true` 로 남긴다

항목 하나를 버리는 것과 그날 하루를 통째로 비우는 것은 다르다. 억지로 채운 글이
쌓이는 것도 해롭지만, **예약 발행이 몇 주째 아무것도 올리지 않는 것은 기능이
고장 난 것과 구분되지 않는다.** 위 "하루 최소 한 편"을 먼저 읽는다.

## 끝내기 전에 반드시 확인한다

실행을 마치기 전에 **실제로 push되었는지 눈으로 확인한다.** 썼다고 생각하는 것과
올라간 것은 다르다.

```bash
git log origin/claude/personal-editable-homepage-31hofg --oneline -5
git status --short
```

- 오늘 쓴 글의 커밋이 `origin/...` 로그에 보이는가?
- `git status` 에 커밋되지 않은 글 파일이 남아 있지 않은가? 남아 있으면 지금
  커밋하고 push한다. **작업 트리에 글을 남겨 둔 채 실행을 끝내지 않는다.**

## 완료 보고

무엇을 발행했고 무엇을 버렸는지, 버린 이유와 함께 남긴다.
발행한 글은 **커밋 해시와 함께** 적는다. 한 편도 올리지 못했다면 검토한 후보와
각각을 버린 이유를 적는다.
