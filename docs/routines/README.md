# 예약 실행 (Routines)

자동 발행은 네 개의 예약 실행이 담당한다. 앞의 셋은 **새 세션**으로 시작해
이 저장소를 새로 받아 오고, 아래 파일 하나를 읽어 그대로 수행한다. 어떤
실행도 다른 대화 세션이 열려 있는지와 무관하게 돌고, 권한은 완전
자동(auto)이라 사람의 승인을 기다리지 않는다.

| 예약 | cron (UTC) | 한국시간 | 읽는 파일 | 모델 |
| --- | --- | --- | --- | --- |
| 아침 브리핑 | `0 21 * * *` | 매일 06:00 | `daily.md` | Sonnet |
| 아침 브리핑 감시 | `40 21 * * *` | 매일 06:40 | `watchdog.md` | Sonnet |
| 발행 요약 메일 | `5 22 * * *` | 매일 07:05 | `email-summary.md` | (기존 세션) |
| 글 요청 처리 | `8 */12 * * *` | 12시간마다 | `requests.md` | Sonnet |

앞의 세 파일(daily.md·watchdog.md·requests.md)이 실제 지침은 아니다.
지침은 `docs/daily-brief.md` 한 곳에 있고, 이 파일들은 "무엇을 하는
실행인지 + 그 문서를 읽어라" 만 적는다. `watchdog.md` 만 예외로, 이
파일 자체가 지침이다 — 감시 실행은 daily-brief.md의 다섯 편 규칙을 그대로
따르지 않고 "최소 한 편"만 노리기 때문이다.

`email-summary.md` 는 나머지 셋과 구조가 다르다. **새 세션이 아니라 기존
대화 세션에 직접 묶여 있다** — 이 조직에서는 새 세션에 Gmail 같은
커넥터를 붙이는 것이 API로 막혀 있어서, 이미 Gmail이 연결된 세션을 깨워
쓰는 우회로를 택했다. 자세한 이유와 한계(세션이 바뀌면 다시 만들어야
한다는 점 포함)는 그 파일에 있다.

## 왜 프롬프트를 저장소에 두는가

예약 설정 안에만 프롬프트가 있으면 아무도 그것을 읽지 않는다.
실제로 도메인을 `justies.net` 으로 옮긴 뒤에도 두 프롬프트에는 옛 주소가
그대로 남아 있었다 — 저장소를 grep 해도 나오지 않는 자리에 있었기 때문이다.
파일로 옮겨 두면 사이트를 고칠 때 같이 눈에 걸린다.

예약 설정에 남는 프롬프트는 네 줄짜리 포인터뿐이므로, 지침을 고칠 때
예약 설정을 건드릴 필요가 없다.

## 무엇을 고치면 어디에 영향이 가는가

| 고치고 싶은 것 | 고칠 곳 |
| --- | --- |
| 글의 규칙 (섹션, 출처, 문체, 도표) | `docs/daily-brief.md` |
| 실행의 역할 설명 | `daily.md` · `requests.md` · `watchdog.md` · `email-summary.md` |
| 실행 시각 | 예약 설정의 cron |
| 모델 | 예약 설정 (`email-summary` 는 세션 고정이라 모델도 그 세션 것을 그대로 쓴다) |

## 왜 Sonnet인가

글을 쓰는 세 작업(아침 브리핑·감시·글 요청 처리)은 판단보다 **절차 준수**가
전부다. 무엇을 쓸지는
`docs/daily-brief.md` 가 이미 정해 두었고, 실행은 그것을 따라 자료를 열고,
사실과 해석을 나누고, 빌드를 통과시키고, 커밋한다. 여기서 비싼 모델이
더 잘하는 부분은 크지 않다.

대신 절차가 지켜지지 않으면 조용히 틀린 글이 발행된다. 그래서 지침은
"알아서 판단하라" 가 아니라 검사 가능한 문장으로 적혀 있다 —
원문을 열었는가, 발행일을 확인했는가, 미확인을 미확인이라고 적었는가.
Sonnet으로 내리는 대신 지침을 조이는 쪽을 택했다.

## 작업 브랜치

발행되는 글은 **사이트가 배포되는 브랜치**로 간다
(`claude/personal-editable-homepage-31hofg`). 사이트를 배포하는 브랜치는
하나뿐이므로, 다른 브랜치에 쌓으면 글이 올라가지 않는다.

자동화 자체를 손볼 때는 `claude/auto-publish-sonnet` 에서 작업하고
검증한 뒤 배포 브랜치로 합친다. 이 문서와 두 프롬프트 파일이 그 대상이다.
