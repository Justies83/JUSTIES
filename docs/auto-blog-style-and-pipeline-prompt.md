# 자동 발행 블로그 — 문체·규칙·파이프라인 프롬프트 (이식용)

이 블로그(justrnafather.blogspot.com 뉴스 자동 발행 + justies.net 아침 브리핑)에서
실제로 쓰고 있는 문체 규칙과 자동 발행 파이프라인을 다른 블로그에 옮기기 위해
정리한 문서다. **플랫폼을 정하지 않은 상태에서도 그대로 쓸 수 있게**, 발행
API처럼 블로그마다 다른 부분은 `[ ]`로 표시해 뒀다. 새 블로그를 붙일 때 그
부분만 채우면 된다.

이 문서 전체를 시스템 프롬프트/지침 문서로 그대로 붙여써도 되고, 필요한
절만 떼어 써도 된다.

---

## 0. 이 담당자가 하는 일 (요약)

트렌드나 최신 소식에서 주제를 하나 고르고, 근거 기사 여러 건을 확인한 뒤,
아래 문체 규칙을 지켜 글 한 편을 쓰고 블로그에 발행한다. 사람이 매번 지시하지
않아도 반복 실행되는 것을 전제로 한다 — 그래서 "중복 방지", "실패 시 무엇을
할지", "한 편 끝날 때마다 커밋" 같은 운영 규칙이 문체 규칙만큼 중요하다.

## 1. 문체·내용 규칙 (플랫폼과 무관 — 그대로 이식)

### 1.1 어투

- 문장은 모두 **"~습니다"** 로 끝낸다. "~했다", "~밝혔다" 같은 신문 기사체를
  쓰지 않는다. 제목·표·태그는 예외.
- 담백한 평서문. 과장된 수식어, 낚시성 표현을 쓰지 않는다.
- 판단(추측·해석)과 사실을 섞지 않는다. 판단에는 "~로 보입니다", "~로
  읽힙니다" 처럼 판단임이 드러나는 표현을 쓴다.

### 1.2 절대 쓰지 않는 표현

**자기 언급 금지** — 이 글이 어떻게 기획됐는지는 독자와 상관없다.
- "이 글에서는", "살펴보겠습니다", "정리해 보았습니다", "알아보겠습니다",
  "위에서 살펴본 바와 같이", "결론적으로", "종합하면"
- 검색어·검색량·실시간 순위·트렌드에 대한 언급 — 자동 생성 사실 자체를
  드러내지 않는다.

**속 빈 상투어 금지** — 정보 없이 문장만 늘리는 표현.
- "주목받고 있습니다", "이목이 집중되고 있습니다", "눈길을 끌고 있습니다",
  "관심이 쏠리고 있습니다", "화제가 되고 있습니다", "귀추가 주목됩니다",
  "중요한 과제로 떠올랐습니다", "다양한", "많은 사람들이"

**단정·과장 금지**
- "100% 보장", "무조건", "반드시" 같은 확언, 수익·효과를 약속하는 표현.
  조건과 한계, 아직 정해지지 않은 부분을 함께 적는다.

**지어낸 1인칭 체험담 금지**
- "제가 직접 해보니", "저도 그랬습니다" — 겪지 않은 개인 경험을 지어내지
  않는다. (직접 겪은 후기·리뷰 코너는 예외로 두되, 그건 이 자동 파이프라인의
  대상이 아니다 — 아래 "3.6 자동 발행 대상에서 뺄 것" 참고.)

### 1.3 구성 원칙

- **첫 문단은 배경 설명이 아니라 가장 중요한 사실로 시작한다.** 독자가 이
  주제를 찾아본 이유부터 답한다.
- 전문 용어·제도 이름·약어는 처음 나올 때 한 구절로 풀어 준다. 다만 사전식
  정의를 늘어놓지 않는다 — 그 사실이 독자에게 무슨 뜻인지까지 붙인다.
- 언제·얼마·누가·어떤 절차인지 구체적으로 쓴다. 해당되는 사람과 아닌 사람,
  예외, 헷갈리기 쉬운 지점을 구분한다.
- 한 문단에는 한 가지 생각만. **조건·항목이 셋 이상이면 문단으로 풀지 않고
  표나 소제목으로 나눈다.**
- 주제어를 기계적으로 반복하지 않는다. 검색을 의식해 쓴 문장은 독자가
  바로 알아챈다.
- 분량은 본문 1500~2500자, 문단은 3~5문장.

### 1.4 FAQ 코너를 만들지 않는다 (중요)

**따로 묻고 답하는 코너를 만들지 않는다.** 독자가 물을 법한 것("얼마나
걸리나", "누가 대상인가", "예외는 없나")을 문답 형식으로 글 끝에 떼어
놓지 말고, 해당하는 절이나 문단 안에 자연스러운 서술로 풀어 넣는다.
사람이 쓴 기사는 글 끝에 자문자답을 붙이지 않는다 — FAQ 코너는 기계적으로
찍어낸 글의 가장 흔한 티다.

(이 블로그도 처음엔 FAQ 3~5개를 JSON 스키마에 넣었다가, 나중에 전부 없애고
이미 발행된 50여 편을 다시 써서 본문 서술로 접었다. 처음부터 넣지 않는 것이
싸다.)

### 1.5 근거·정확성

- 근거 기사에 없는 사실(숫자, 날짜, 발언, 인용)을 지어내지 않는다.
  확실하지 않으면 "보도에 따르면", "아직 확인되지 않았다"처럼 불확실성을
  드러낸다.
- **발행 날짜를 반드시 확인한다.** 검색은 오래된 기사를 최신처럼 보여준다.
  날짜가 확인되지 않으면 그 소식은 버린다.
- 검색 결과 요약만으로 쓰지 않는다. 원문을 열어 숫자·고유명사·인용문을
  대조한다.

### 1.6 분류(카테고리) 체계

**고정된 카테고리 목록**을 정해 놓고 매 글에 하나씩 붙인다. 목록은 새
블로그의 주제 범위에 맞게 바꾸되, 개수는 4~6개 정도가 적당하다(너무 많으면
분류가 갈리고, 너무 적으면 다 "기타"로 몰린다). 이 블로그가 쓰는 예:

```

```

모델이 목록 밖의 말을 냈을 때를 대비해 **기본값(생활·정보처럼 가장 넓은
분류)** 을 하나 정해 둔다.

### 1.7 특정 주제군 자동 제외 — 2단계 키워드 필터 패턴

이 블로그는 연예·스포츠를 자동 발행 대상에서 뺀다. 그 판정 로직이 재사용
가치가 있는 패턴이라 일반화해서 남긴다.

**문제**: 키워드 하나로 판정하면 오탐(예: "감독"은 영화감독일 수도, 인사
기사일 수도 있다)이 나고, 여러 키워드가 다 걸려야 한다고 하면 근거 기사가
적을 때(1~2건) 놓친다. 실제로 이 블로그에서 근거 기사 3건 중 1건에만 "가수"가
붙어서 옛 기준(2건 이상)을 통과해 연예 글이 그대로 나간 사고가 있었다.

**해법**: 키워드를 두 등급으로 나눈다.
- **확실한 낱말** — 다른 맥락에서 쓰이는 일이 거의 없다(가수, 아이돌, 컴백,
  올림픽, 홈런, KBO …). **한 건만 걸려도** 그 주제를 막는다.
- **애매한 낱말** — 다른 분야 기사에도 나온다(감독, 이적, 대표팀, 리그 …).
  **두 건 이상** 걸릴 때만 막는다.
- 출처(매체) 이름도 따로 봐서, 스포츠·연예 전문 매체가 근거로 잡히면 그
  자체로 확실한 신호로 취급한다.
- 검색어(주제) 자체가 이 낱말들에 걸리면 근거 기사를 볼 필요 없이 바로
  막는다.

이 패턴은 "연예·스포츠 제외"뿐 아니라, 새 블로그에서 자동 발행하고 싶지
않은 다른 주제군(예: 정치적으로 민감한 주제, 특정 브랜드 홍보성 기사 등)을
거를 때도 그대로 쓸 수 있다.

### 1.8 사진

두 가지 방식 중 하나를 고른다 — **법적 위험과 노력의 트레이드오프**이므로
새 블로그의 성격에 맞게 선택한다.

**A. 기사 원문 사진을 가져온다** (이 블로그의 Blogspot 뉴스 자동 발행이 쓰는
방식)
- RSS가 주는 썸네일(대개 200px 안팎)은 쓰지 않는다. 기사 원문 페이지를
  열어 `<meta property="og:image">` 값을 읽으면 실제로 그 기사에 실린,
  훨씬 큰 보도사진을 얻을 수 있다.
- 출처 링크를 사진 캡션에 반드시 남긴다("기사 보기" 링크).
- 저작권 리스크가 있는 방식이다 — 언론사 사진을 그대로 임베드하는 것이므로,
  법적으로 더 안전하게 가려면 B를 쓴다.

**B. 사진을 쓰지 않고 직접 만든 도표/커버로 대체한다** (이 블로그의
justies.net 아침 브리핑이 쓰는 방식)
- 언론사 사진·기업 배포 자료를 아예 쓰지 않는다.
- 대신 기사에 실린 수치로 SVG 도표를 직접 그리거나, 분류·글 제목 해시로
  결정되는 추상적인 커버 이미지를 자동 생성한다. 매번 다르고, 다시 빌드해도
  같은 결과가 나오게 만든다.
- 다크모드까지 고려한 배경·글자색 팔레트를 하나 정해 고정한다(이 블로그는
  종이색 `#f4f1ea` 배경에 틸 `#16756a`/산호 `#e0795b` 강조색을 쓴다).

### 1.10 마크다운으로 쓸 때만 해당하는 함정 (플랫폼이 마크다운을 쓸 경우)

Blogspot처럼 HTML을 직접 조립해 보내면 이 문제가 없다(escaping 함수가
따로 처리한다). 하지만 마크다운 소스 파일을 쓰는 플랫폼(Jekyll, Hugo,
Astro content collection 등)이라면 한국어 본문에서 실제로 반복해서 사고가
난 두 가지를 반드시 지침에 넣는다.

**물결표(`~`)는 escape 한다.** 한 단락(또는 목록 항목) 안에 `~`가 두 번
나오면 마크다운이 그 사이를 **취소선**으로 만들어 버린다. 구간 표기(`6~12억원`,
`2028~2029년`)가 많은 글에서는 반드시 걸린다.

```markdown
과세표준 6\~12억원 구간 ... 최종 구조는 2028\~2029년에 완성된다
```

한 줄에 물결표가 하나뿐이면 안전하지만, 세는 것보다 **항상 escape하는
것이 싸다.**

**볼드가 문장부호로 끝나고 그 뒤에 조사가 공백 없이 붙으면 깨진다.**
`**47.2%**를`, `**"전혀 없다"**고` 같은 형태 — 한국어는 조사가 항상 앞말에
붙기 때문에, 수치·인용을 볼드로 감쌀 때마다 마주치는 문제다. 글자로 끝나는
볼드(`동결**됐고`)는 문제없다.

```markdown
전체 수출의 **47.2%**를 차지했다     ← 깨짐
전체 수출의 **47.2**%를 차지했다     ← 정상 (숫자만 볼드, %는 밖으로)
김 장관은 **"이해가 있었다"**고 밝혔다   ← 깨짐
김 장관은 **"이해가 있었다"고** 밝혔다   ← 정상 (조사까지 볼드에 포함)
```

고치는 방법은 둘 중 하나 — 문장부호를 볼드 밖으로 빼거나, 뒤에 붙는 조사를
볼드 안으로 끌어들인다.

## 2. 자동 발행 파이프라인 (플랫폼에 무관한 뼈대)

한 바퀴(한 편 발행)는 아래 순서로 돈다. 순서 자체는 플랫폼과 무관하다.

```
1) 주제 수집        구글 트렌드 RSS / 뉴스 검색 등에서 후보 주제를 받는다
2) 중복 제거        이미 쓴 주제인지 두 군데로 대조한다
3) 근거 수집        후보 주제로 관련 기사를 최소 3건 모은다 (부족하면 검색으로 보충)
4) 필터             자동 발행 대상에서 뺄 주제군을 1.7의 2단계 필터로 제외
5) 본문 생성        LLM에 구조화된 JSON 스키마로 요청 (모델 폴백 목록을 순서대로 시도)
6) 조립             JSON → HTML/마크다운으로 렌더링 (사진·표·참고기사·태그 포함)
7) 발행             플랫폼 API로 올린다 (라벨/카테고리 포함)
8) 기록             발행 기록 파일에 남긴다 (다음 회차의 중복 판정용)
```

### 2.1 주제 수집

- 구글 트렌드 RSS(`https://trends.google.com/trending/rss?geo=<국가코드>`)가
  기본 소스다. 키워드마다 관련 기사 몇 건과 대표 사진이 이미 붙어 있어 편하다.
- 트렌드 RSS의 기사 목록이 빈약하면 뉴스 검색으로 보충한다. **빙 뉴스 RSS를
  구글 뉴스 RSS보다 우선한다** — 빙의 리디렉션 링크는 `url=` 쿼리 파라미터에
  실제 기사 주소가 그대로 들어 있어 원문에서 사진을 꺼낼 수 있지만, 구글
  뉴스(`news.google.com`)의 리디렉션은 단순 HTTP 요청으로는 실제 기사로
  풀리지 않는다.

### 2.2 중복 제거

두 군데를 대조한다 — 둘 중 하나만 쓰면 어느 쪽이든 구멍이 난다.
- **저장소에 커밋되는 발행 기록 파일** (예: `state/published.tsv`) — 시각,
  검색어, 제목을 탭으로 구분해 쌓아 둔다. 최근 N건만 남기고 잘라낸다.
- **블로그의 공개 피드에 실제로 올라간 최근 글 제목** — 기록 파일이 어떤
  이유로든 씹혔을 때(예: 커밋이 실패했는데 발행은 됐을 때) 이쪽이 진실이다.

### 2.3 본문 생성 — LLM 호출 규칙

**모델 폴백 목록을 순서대로 시도한다.** 무료/저가 티어를 쓰면 특정 모델이
그날 갑자기 한도(429)에 걸리거나 서비스가 몰려 503이 나는 일이 흔하다.
한 모델이 막히면 다음 모델로 넘어가는 폴백 체인이 없으면 그 회차는 통째로
실패한다.

- 429·5xx는 **한 번 정도는 몇 초 기다렸다가 재시도**할 가치가 있다. 완전히
  응답이 없는(타임아웃) 경우는 재시도 자체가 그 시간을 또 날리므로, 남은
  모델이 있으면 바로 다음으로 넘어간다.
- 호출 전에 그 API 키로 실제로 쓸 수 있는 모델 목록을 한 번 물어보고,
  존재하지 않는 모델 이름에 매번 요청을 날려 시간을 버리지 않는다. 모델
  이름은 자주 바뀌므로(구버전이 폐기되거나 신버전이 나옴), 코드에 이름을
  하드코딩하는 대신 그때그때 살아있는 후보로 보강한다.
- **응답 형식을 JSON 모드로 못 박는다** (API가 지원하면). 프롬프트로
  "JSON만 답하라"고 부탁하는 것보다 훨씬 확실하다 — 설명 문장이나 코드펜스가
  섞여 오지 않는다.
- **출력 토큰 상한을 넉넉히 둔다.** 너무 작으면 응답이 중간에 잘려 JSON
  파싱이 실패하고, 표나 뒷부분 섹션이 통째로 사라진 글이 나온다. 응답의
  종료 사유(finish reason)가 "토큰 상한"이면 그 응답을 의심한다.
- **JSON 파싱은 너그럽게 짠다.** 코드펜스(\`\`\`json ... \`\`\`)를 벗겨내고,
  첫 `{`부터 마지막 `}`까지만 취하고, 마지막 요소 뒤에 붙는 흔한 쉼표
  실수는 한 번 고쳐서 재시도한다.
- **파싱이 완전히 실패했을 때의 대비책을 정해 둔다.** 이 블로그는 두 가지
  경로가 다르게 처리한다 — 정기 자동 발행(auto_post.py)은 실패한 응답을
  문단 단위로 쪼개 최소한의 형태로라도 발행하고, 기존 글 일괄 재작성
  배치(rewrite_existing.py)는 그 글만 건너뛰고 나머지를 계속 진행한다.
  **일괄 처리 스크립트는 한 편 실패가 전체를 막지 않게** 만들고, 실패한
  것만 나중에 골라 재시도할 수 있게 id 목록을 받는 옵션을 넣어 둔다.

**JSON 스키마 예시** (이 블로그가 쓰는 것 — 그대로 가져다 써도 됨):

```json
{
  "title": "무슨 일인지 알 수 있는 30자 내외의 제목",
  "summary": "글 전체를 한 문단(2~3문장)으로 요약",
  "sections": [
    {"heading": "소제목", "paragraphs": ["문단", "문단"]}
  ],
  "table": {
    "caption": "표 제목",
    "headers": ["항목", "내용"],
    "rows": [["행1-1", "행1-2"]]
  },
  "category": "<1.6의 카테고리 목록> 중 하나",
  "tags": ["태그", "태그"]
}
```

`sections`는 3~6개, `table.rows`는 있을 때 3~6개로 만들게 프롬프트에 못
박는다. `table`은 조건·항목이 셋 이상일 때만 채우게 한다(1.3 참고).

### 2.5 조회수 표시(선택)

독자에게 글마다 조회수를 공개하고 싶다면, 플랫폼에 그런 기능이 없을 때
무료 방문자 카운터 배지 서비스(이미지 하나를 GET으로 요청하면 카운트가
올라가는 방식, 예: visitor-badge.laobi.icu)를 글 주소별로 심는 방법이 있다.

- **글 주소는 발행해야 알 수 있다** — 그래서 처음 발행할 때는 자리표(예:
  `<!--VIEW_COUNTER-->`)만 넣고, 발행 API가 글 주소를 돌려주면 그 주소로
  배지 URL을 채워서 **한 번 더 수정(update) API를 호출**한다.
- **배지 이미지를 본문 맨 앞에 두지 않는다.** 많은 플랫폼이 본문의 첫
  `<img>`를 SNS 공유 미리보기 대표 이미지로 자동 선택한다. 배지가 첫
  이미지가 되면 공유 미리보기에 사진 대신 작은 카운터 아이콘이 뜬다.
  실제 사진(있다면) 뒤에 배지를 놓는다.
- 이런 서비스는 수명이 짧다 — 오래된 서비스(hits.seeyoufarm.com 등)가
  도메인 자체가 죽는 일이 있었다. 이미지 하나일 뿐이라 서비스가 죽어도
  페이지가 깨지지는 않고 깨진 이미지 아이콘만 남는 정도라, 리스크는 낮다.

### 2.6 운영 규칙

- **한 편 끝날 때마다 커밋·push한다.** 여러 편을 모아 마지막에 한꺼번에
  커밋하지 않는다 — 실행이 중간에 끊기면(시간 제한, 에러) 그때까지 쓴 글이
  전부 사라진다. 실제로 이 사고가 여러 번 났다.
- **일괄(batch) 작업 전에는 원본을 백업한다.** 기존 글을 대량으로
  덮어쓰는 작업(예: 문체 통일, 재작성)을 돌릴 때는 각 글의 원본을
  타임스탬프 폴더에 그대로 저장해 두고 커밋한다. 무엇이 잘못돼도 되돌릴
  수 있게.
- **스케줄 실행은 동시 실행을 막는다.** 예약 실행과 수동 실행이 겹치면
  같은 주제로 두 편이 나가거나 상태 파일이 꼬인다. CI에서 동시성 그룹으로
  묶어 겹치지 않게 한다.
- **종료 코드로 "정상적으로 쓸 게 없었음"과 "고장"을 구분한다.** 트렌드가
  다 이미 쓴 주제거나 근거 기사가 없어서 이번 회차를 건너뛴 것은 에러가
  아니다. 이걸 실패로 처리하면 로그가 매번 빨갛게 떠서, 진짜 고장이 났을
  때 구분이 안 된다.
- **자격증명만 빠르게 확인하는 모드를 하나 둔다** (`--check`류). 트렌드도
  LLM도 건드리지 않고 인증 토큰 발급과 API 연결만 확인하면 20초 안에
  끝나서, 시크릿을 새로 설정했을 때 바로 확인할 수 있다.

### 2.7 자동 발행 대상에서 뺄 것

이 파이프라인은 **직접 겪지 않으면 쓸 수 없는 글**(개인 리뷰, 체험담,
육아 일기 등)에는 쓰지 않는다. 사실 확인이 불가능한 주제를 억지로
자동 생성하면 위 1.2의 "지어낸 1인칭 체험담" 문제가 바로 생긴다. 그런
카테고리는 자동 발행 대상 목록에서 처음부터 뺀다.
